No provider is needed for indexing, context, impact, `verify` or `coverage`. Providers matter only for live
[missions](/repo-ai/docs/missions/), [tournaments](/repo-ai/docs/tournaments/) and
[handoffs](/repo-ai/docs/handoff/). This page records observations, not endorsements.

## Checking providers locally

```sh
repo-ai agents list      # is an executable present? no subprocess, no model call
repo-ai agents doctor    # sandboxed --help/--version probes; no login check, no model call
repo-ai agents route     # what --agent auto would choose, with a status class
repo-ai agents setup claude|opencode|codex   # how that provider authenticates inside repo-ai; no model call
repo-ai agents catalog   # 24 coding agents and what repo-ai can honestly do with each
```

`agents route` reports a `status_class` such as `NOT_INSTALLED`, `NOT_AUTHORIZED`, `BLOCKED_AUTH`, `BLOCKED_QUOTA`,
`BLOCKED_SANDBOX`, `UNSUPPORTED` or `ISOLATED_READY`. There is no "host ready" state: repo-ai has no un-isolated
execution path. Routing checks offline whether a provider has any login repo-ai's isolation can use (`SETUP_REQUIRED`,
reported as `BLOCKED_AUTH`) without reading credentials; it does not check quota before a live run.

### ACP conformance kit (agents without an adapter)

```sh
repo-ai agents conformance --acp-executable /absolute/path/to/agent --acp-arg acp [--json]
```

For an [Agent Client Protocol](https://agentclientprotocol.com) agent repo-ai has no adapter for, this checks whether
the executable you name answers `initialize` with ACP 1, and records who it says it is and what it advertises. It
runs only that handshake, in the probe sandbox `agents doctor` uses: no session, no model call, no network, no
LaunchServices or Apple events, writes only to a scratch directory, every process it starts swept afterwards, and
never a repository-owned executable. Agent-supplied text is stripped of terminal escapes and bounded. Verdicts:
`HANDSHAKE_CONFORMANT`, `NOT_ACP` (it answered, not with ACP 1), `NO_HANDSHAKE` (it exited or stayed silent; what it
printed is shown, redacted), `REFUSED`, `NO_SANDBOX`. Passing says the agent speaks the protocol. It does not make it
an execution provider: that needs an adapter with its own isolation and conformance tests, and every such agent stays
`PLANNED` until then. Observed on 2026-10-31: Gemini CLI 0.65.0 (`--acp-arg=--acp`) conforms; OpenCode 2.2.1 does not
start without network (its ACP mode runs its own local server) and reports `NO_HANDSHAKE` with that reason.

## Per-provider notes

### IBM Bob

Last live-verified on an earlier pre-release; not re-run on 0.9.0 or 0.10.0, and its account entitlement was not
re-checked. Install and log in to Bob as its documentation describes. repo-ai passes your `--max-cost-usd` to Bob's own cost cap,
so a positive ceiling is enforced by the provider. Cost figures are provider-reported, not billing records.
repo-ai copies your `~/.bob/settings` directory into the run's scratch HOME and passes `BOB_API_KEY` if it is set;
both are readable inside the run.

### Codex CLI

Log in with Codex's own flow; better, give repo-ai a separate login (`CODEX_HOME=<dir> codex login`, see
`repo-ai agents setup codex`). repo-ai runs Codex with a scratch `HOME` holding only that login's token and the
model-selection keys of your config (no MCP servers or `notify`), under repo-ai's outer sandbox, which from 0.10.0
hides the rest of your `HOME`. The token copy itself is readable by Codex's model, which has a shell and the network:
a prompt-injected repository could try to send it out, which is why a separate, revocable login is recommended. Because nested sandboxes are not supported on macOS, repo-ai passes Codex's
`--dangerously-bypass-approvals-and-sandbox` **only after** confirming its outer sandbox is active for that run; if it
is not, the run is refused. The outer sandbox is then the only write boundary. Codex has no hard USD flag, so a
positive `--max-cost-usd` is refused and cost is recorded as `UNKNOWN`, never `0`. Bound runs with `--max-seconds`.

**Experimental: credential broker** (`REPO_AI_CODEX_BROKER=1`, macOS only; live-verified with a ChatGPT login on Codex 0.165, not yet with an API-key login). With the broker,
no token is copied into the sandbox at all:
- Codex gets a per-run dummy key and a model provider pointing at a loopback proxy inside repo-ai.
- The proxy accepts only `POST /v1/responses` with that dummy key, swaps in the login's credential, and forwards the
  request upstream without following redirects.
- Codex's sandbox can reach that one loopback port and nothing else, and it cannot read the login's directory, even
  one outside your `HOME`. A prompt-injected repository has no token to read and no host to send one to.
- The model can read the dummy key and send its own requests, so each request is vetted:
  - only tools that Codex runs locally are forwarded;
  - the hosted web search is removed;
  - a remote image or file URL is refused, because the upstream would fetch it;
  - the model is pinned to the one named in Codex's first request;
  - stored server-side state (a stored prompt, conversation or response, or a background run) is refused.

  As a result, a Codex sub-agent on a different model, or any Codex endpoint other than `/v1/responses`, is refused
  in brokered runs.
- An expired ChatGPT token is refused, never refreshed: run `codex login` for that login.
- A run whose upstream rejects the credential, or that sends nothing through the broker, is a failure.

Offline tests cover all of this. Two live runs on 2026-10-31 confirmed that the ChatGPT backend accepts the forwarded
requests; a run's `codex_broker` record shows the mode, model, request count and statuses, never a credential.

### Antigravity (`agy`, macOS only)

agy has no scratch-HOME login, so it runs with the real `HOME`, but the seatbelt profile denies reads under `HOME`
except its own state directory (minus history), `~/.gemini/config`, `~/.local` and the two keychain database files it
needs to authenticate. Those files are encrypted, but the agy process can read them and has network access. repo-ai
runs it headless with edits only, shell actions denied, and never with `--dangerously-skip-permissions`. If that
exposure is unacceptable to you, do not use `--agent agy`.

### Claude Code

From 0.10.0 an isolated mission provider (macOS live-verified; Linux by tests only). It uses Claude Code's own login
and nothing is copied: either `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`; not yet live-verified) or a
separate repo-ai login (`CLAUDE_CONFIG_DIR=<dir> claude auth login`; `repo-ai agents setup claude` prints the exact
command). The model gets file tools only, with no shell, web, MCP, skills or hooks; before every live run repo-ai
starts the session once with a model name Claude Code rejects locally and refuses the run if anything else would load
(an account can sync plugins and connectors into every login). `--max-cost-usd` maps to Claude's own cap, which is
checked between turns: one turn of overshoot was observed. Claude is also a **host** (`repo-ai init --agent claude`).

### OpenCode (local model, macOS only)

Account-free: OpenCode runs against a loopback model endpoint such as Ollama (`ollama pull qwen3:8b`, then
`export REPO_AI_OPENCODE_MODEL=qwen3:8b`; `repo-ai agents setup opencode`). The sandbox allows network to loopback
only (no other host is reachable; on macOS this also admits your machine's own network addresses and lets the agent
listen on every interface: see [Security](/repo-ai/docs/security/#live-provider-runs)), a deny-by-default tool policy allows read, edit, glob, grep and list, project configuration is ignored and
cloud-routed models are refused. Small local models are weak at this: in recorded journeys several attempts failed
(repo-ai refused them) and one passed the visible tests while dropping a requirement that no test pinned.

### Gemini CLI (removed)

Gemini CLI was superseded by Antigravity (`agy`, above), so repo-ai no longer has a `gemini` provider. Before its
removal, the tested account was rejected (exit 41, 2026-10-30).

## What every live run shares

- Live calls happen only with `--run --allow-live-provider`.
- The task text and the workspace files the agent opens go to that provider, under that provider's terms.
- Network is allowed for the provider process (the model API needs it), so it can send what it can read.
- Subscription quota and unknown dollar cost are separate from any spending ceiling you set.

Details: [Security & privacy](/repo-ai/docs/security/#live-provider-runs).
