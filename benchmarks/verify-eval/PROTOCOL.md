# verify-eval: does `repo-ai verify` pick the tests that catch real regressions, at lower cost?

**Frozen on 2026-10-21, before any selection was measured on a held-out
project.** Changes made after a held-out result is seen are reported as such.
They never silently replace the first result.

**Scope:** an offline, model-free evaluation of change-based test selection.
It does not measure whether coding agents produce better code. That would
need a separate, pre-registered model experiment.

## Corpus

`corpus.json` pins 15 public, permissively licensed repositories at exact
commits.

| Set | Python | JavaScript (Node `node:test`) | Use |
|---|---|---|---|
| **dev** | cachetools, Python-Markdown, pyflakes, simplejson, tomli | geojson-vt, webidl-conversions | building and debugging the engine |
| **held-out** | peewee, pyfakefs, elementpath, genshi, pathspec | culori, busboy, simple-statistics | measured once, after the engine is frozen |

**Earlier benchmark sets are kept separate.** The `final` and `sealed-v2`
coding tasks are not used. Five of the dev projects are upstream versions of
earlier benchmark bases.

**Replacement rule (held-out).** Applied before any selection result is seen:
- **When:** a project's suite cannot run offline in the sandbox, meaning more
  than half of its test files fail at the pinned commit.
- **With what:** the next project in `reserve` that can.
- **Records:** the replacement and the reason.

## Changes (ground-truth regressions)

**Generated by fixed rules per project.**

1. **Real reverts:**
   - The source-only part of a recent upstream commit (no test files) is
     reverse-applied to the pinned snapshot.
   - Eligible commits are the newest non-merge commits first, changing 1–5
     source files and 2–200 lines, that reverse-apply cleanly.
   - At most 10 per project.
   - This re-introduces real code as it was before a real change.
2. **Operator mutations:** 20 per project, with a seeded RNG.
   - **What:** one site in one source function is flipped:
     - a comparison (`<`↔`<=`, `==`↔`!=`);
     - arithmetic (`+`↔`-`);
     - a boolean (`and`↔`or`, `true`↔`false`);
     - an integer constant (+1);
     - `return x` → `return None` / `return undefined`.
   - **Python:** done through `ast` with unparse of that one function, other
     lines untouched.
   - **JavaScript:** done as a token substitution on one line.

**Ground truth:**
- Every test file is run **individually** in a network-less podman sandbox,
  once at the snapshot (baseline) and once per change.
- A change's **affected set** is the test files that pass at baseline and fail
  with the change.
- Only changes with a non-empty affected set ("detected") are scored for
  misses. Undetected changes are counted and reported.

## Methods compared

All methods run on the same change, as an uncommitted working-tree diff
against the snapshot.

| Method | What it selects |
|---|---|
| `all` | every test file (the cost ceiling) |
| `impact-0.7.7` | `repo-ai impact <changed files>` from the previous release (static, depth 3) |
| `grep` | test files that import the changed module, or mention a changed function name, or (JS) import the changed file's name |
| `verify-static` | `repo-ai verify` without runtime evidence |
| `verify-runtime` | `repo-ai verify` with runtime evidence recorded at the snapshot (`--record`) |
| `policy-static` / `policy-runtime` | the workflow `verify` recommends: its selection, plus the full suite whenever confidence is **low** |

## Metrics (per method, per set)

**Correctness:**
- **no-miss rate:** the share of detected changes whose affected set lies
  entirely inside the selection;
- recall;
- misses, broken down by the confidence the method reported.

**"Unsupported confidence"** means a miss at confidence **high**, or at
**medium** with no trigger. These are the dangerous errors.

**Efficiency:**
- the selected share of test files;
- the share of suite **time**, from per-file baseline durations.

**Commands:** every per-file command repo-ai suggests must collect and run at
least one test at baseline. Anything else counts as a fabricated or invalid
command.

**Latency:** plan time per change and `--record` time per project.

## Targets (from the mandate; stretch goals, not results)

- **Correctness:** ≥ 95% no-miss for the recommended policy on held-out.
- **Efficiency:** a material reduction in suite time at comparable no-miss.
- **Confidence:** zero misses at "high" confidence; no low-risk verdict in a
  dynamic-loading case.
- **Commands:** zero invalid commands.

A target missed is reported as missed. Metrics, thresholds and rules here do
not change after held-out results are seen.

### Amendment 4a (2026-10-23, before any held-out-5 candidate is searched): measurement corrections from the pre-release audit

**Why:** the benchmark audit (`docs/VERIFY-AUDIT-2026-10.md`, "Benchmark
methodology") found weaknesses in how held-out-4 measured speed and
correctness. None changes a held-out-4 result. Held-out-5 measures more, as
follows. Every metric Amendment 4 defines is kept and computed as before, so
the two sets stay comparable.

**Added metrics (all in `wallclock.py`, enabled with `VEV_AMENDMENT_4A=1`):**

1. **Selection without parallelism.**
   - What: after the session, every change again with
     `--rerun --workers 1` (new engine only).
   - Reported as a median, with detection on those runs.
   - The native suite is one process: this separates the effect of
     selection from the effect of running up to 4 processes at a time.
2. **Whether the native suite ran.**
   - The exit code and the last 400 characters of output of each of its
     three runs.
   - A native suite that stops at a collection error is reported as such
     next to its time.
3. **Passing changes not reported as passing.**
   - What: a change with no affected file whose verdict is not one of
     `selected-and-full-suite-passed`, `selected-passed (full suite not run)`
     or `nothing-selected`.
   - Reported per project, alongside the false alarms (which still mean a
     `regression` naming a file the ground truth says is unaffected).
4. **A cold run.**
   - What: the last three changes once more, after removing verify's
     evidence, base-outcome cache, timings, scan cache and gate state. The
     runtime record is kept.
   - Compared with the first run on the verdict *and* on which files are
     reported new and pre-existing.
5. **Aggregates and tails.**
   - The geometric mean of per-project ratios, plus the arithmetic mean, the
     geometric means over failing changes and over passing changes, and the
     largest per-project ratio.
   - The slowest run over native, per project.
   - Computed by `wallclock_tables.py --extended`.
6. **Native time in both passes.** Each engine's pass measures the native
   suite itself. Ratios use the new engine's pass, as in held-out-4; the
   other is recorded for drift.
7. **Audit trail.**
   - Every run carries a start time. A project that is measured again keeps
     its earlier attempt under `_superseded`.
   - Engine order alternates by project, in candidate-list order: odd
     positions run the frozen build first, even positions the previous
     engine first.
   - The selection record lists every candidate whose configuration was
     read, in order, with the decision.

**Targets:** unchanged from Amendment 4. A missed target is written as
"missed".

  baseline run only, never by `verify`.

### Generated changes and ground truth (unchanged)

- `harness.py`: 20 seeded operator mutations and up to 10 real reverts per project.
- Each base-passing test file is run alone in the image, at the base and with each change.
- A change's affected set is the files that pass at the base and fail with it.
- The control's ground truth is its native full suite's exit code per change (`scenarios.py`
  `run_control`), because its runner cannot be split per file.

### Execution measurements (`wallclock.py`, Amendment 4a enabled)

- `N_FAIL = N_PASS = 6`: six failing and six passing changes, interleaved, then three repeats, three
  `--rerun`s, three cold runs and a `--workers 1` pass.
- Run with `VEV_AMENDMENT_4A=1 python wallclock.py --engine new --tag heldout6 …`, with
  `N_FAIL`/`N_PASS` set to 6 by `heldout6.py`. No previous-engine pass.

### Constructed scenarios (`scenarios.py`; labels by construction, validated before use)

**Fixed picks** (`scenarios.picks`):
- **T, T2:** the first and second base-passing test files, by path, among those at or below the
  median baseline duration.
- **Hf, Ff:** the first and last base-passing files by path.
- **M, M2:** the first and second changes, in change order, with a non-empty affected set, no
  time-outs, and every affected file base-passing.
- **P:** the first change with no affected file and no time-out.
- **M_file:** M's single changed source file, if M changes exactly one.

**Injected tests:**
- a test that fails, one that sleeps 10⁵ s (hang), and one that fails with probability ½ (flaky);
- self-contained `unittest.TestCase` classes (collected by unittest and pytest), or `node:test`
  calls (ESM `import` or CJS `require` by the file's own module style);
- appended to an existing test file, or (U2) written as a new file named so that the same discovery
  rules collect it.

| Id | State verified | Label |
|---|---|---|
| U1 | M, staged | new failure |
| U2 | a new untracked test file containing a failing test | new failure (valid only if the reference command collects it) |
| U3 / U4 / U5 | M_file deleted in the worktree / `git rm` / `git mv` to a new name | new failure in every base-passing file that fails without it (valid if ≥ 1) |
| U6 | P staged, M on top in the worktree only | new failure |
| C1 | M, after a passing run of P | new failure; checks `evidence` and the gate |
| C2 | M again after M (regression), P (pass) and a revert: run with reuse allowed | new failure |
| C3 | M2, two `verify --run --rerun` at once | new failure (both runs) |
| C4 | two linked worktrees verified at once: P in one, M in the other | new failure (the M side) |
| C5 | P under `verify --run --rerun`; M written at 0.4 × P's earlier run time; then a run of the final state with reuse allowed | new failure (the final state) |
| C6 | after a passing run of P, every `*.json` under the state directory except `config.json` cut to half its bytes; then M | new failure |
| C8 | M committed; `verify --run --base <original base>` | new failure. The HEAD-relative run is recorded, not scored |
| H1 | a hanging test in T | hang |
| H2 | a hang in Hf and a failing test in Ff | new failure (Ff) |
| H3 | the base already hangs in Hf (`--record` and `--run` with `--timeout 60`); the change makes Ff fail | new failure (Ff) |
| S1 | T already fails at the base; P | no new failure (a pass-like verdict or `failing (all failures pre-existing …)` is correct) |
| S2 | T already fails at the base; a second, new failing test added to T | new failure (validated alone on the pristine file) |
| S3 | M's first affected file already fails at the base (injected); M | new failure |
| S4 | T has a flaky test at the base; P, 3 × `--rerun` | no new failure; false alarms **reported, not gated** |
| S5 | the same flaky base; M, 3 × `--rerun` | new failure (each run) |
| A1 | control project: up to 4 failing and 2 passing changes by its native suite | failing changes: new failure |
| A2 | projects with dependencies: M and P with `--sandbox podman` and no `--image` | M: new failure, scored for G1 only (without the dependencies the base fails the same way, so "pre-existing" is true there). P: recorded, not scored |

**Validation.** Each construction is validated with the harness driver in the image (files alone;
a hang means not finished after 30 s). A scenario that does not validate is invalid: it is reported
with its reason and excluded. **Nothing is rebuilt after a verify outcome is seen.**

### Labels and rules (`score6.py`, frozen)

- **Pass-like:** a verdict starting with one of the three passing prefixes, or exit 0.
- **False assurance (G1), on a valid failing state**, any of:
  - a run with a pass-like verdict;
  - a labelled failing file reported `pass` or `no-tests`;
  - `repo-ai evidence --json` reporting `current` or `same_behaviour` with a passing verdict;
  - `repo-ai verify --gate` silent, with its gate state removed and a fresh session id;
  - a wallclock failing change (or its repeat, rerun or cold run) with a pass-like verdict.
- **New failure reported as pre-existing (G2):** a verdict starting
  `failing (all failures pre-existing`, or a labelled new-failure file classified
  `already failing at the base (the same tests fail)`, or wallclock's `new_as_preexisting`.
- **Runtime no-miss (G3):** wallclock failing changes reported `regression`.
- **False alarms (G4):** wallclock's definition, plus S1 with a `regression` verdict.
- **Tree integrity (G6):** every recorded run's `tree_unchanged`, except the C5 run the scenario
  edits on purpose.
- **Cancellation (G7):** `cancelprobe.py --tag heldout6`, three runs per project, all clean.

### Acceptance thresholds (fixed now; not changed after results)

| Gate | Threshold | If missed |
|---|---|---|
| **G1 false assurance** | **0** | correctness blocker for the runner, environment or scenario class involved |
| **G2 new as pre-existing** | **0** | correctness blocker |
| G3 runtime no-miss | ≥ 95% | reported; misses with a non-pass verdict are not false assurance |
| G4 false alarms | 0 | reported; usability, not a correctness blocker |
| G6 tree unchanged | 100% | safety blocker |
| G7 cancellation | all clean | safety blocker |

**Rule of three:** with 0 false assurances in *n* valid failing states, the one-sided 95% upper
bound on their rate is reported (`1 − 0.05^(1/n)`).

### Performance (`perf6.py`; targets, not gates)

Run with nothing else CPU-heavy on the host:
- planning time per change;
- `--full` against the adaptive run and the native suite;
- the fixed cost of a one-file change against that file run alone (5 each);
- a non-code change;
- interpreter start in the sandbox (10);
- cold, first, reuse and warm-`--rerun` runs (wallclock);
- hang cost (H1, H2);
- the host sandbox against the container on the same session changes (`perf6.py --host`).

**Targets, from earlier mandates:**
- not slower than the native suite (per-project median ratio);
- a hang settled in ≤ 10 s (Python) and ≤ 15 s (node).

A missed target is written as missed.

### Release decision rule (fixed now)

- **G1, G2, G6 and G7 met:** verify's verdicts can be described as supported for the runners and
  environments measured, with the listed limitations.
- **Any G1 or G2 violation:** the runner, environment or scenario class involved is excluded from any
  release claim until a fix is validated on data not used to make it.
- **Speed targets** decide only whether a speed benefit may be claimed, never whether a verdict can
  be trusted.

### Amendment 5a (2026-10-24, after setup and before any `verify` run on the two projects concerned)

**What setup showed:**
- **hb-actions:** `setup` lists **0 test files**. verify's node runner lists test files with
  `NODE_DEFAULT_GLOBS`, which has only `.js`/`.mjs`/`.cjs` names. Node 24's own default discovery
  also runs `*.test.ts` / `*.test.mts` / `*.test.cts`; this was checked with node v24.19.0.
  - This is an engine behaviour: defect **D10**, found here and reported as a held-out-6 finding.
  - Per-file ground truth is impossible, because there is no file to run alone.
- **wcd** (the control): `--record` cannot split an opaque runner, as expected. The truth step
  stopped there.

**Rule:**
- For a project whose engine-listed test universe is empty, and for the control, the ground truth
  of each change is the project's native full suite in its image (`heldout6.py native-truth`).
  - The change is failing if the suite exits 0 at the base and non-zero with the change;
    `truth.json` records it as affected `["<native suite>"]`.
  - A suite that times out (30 min) is recorded and excluded.
- **Constructed scenarios:** these projects take `scenarios.run_control` (A1).
- **Wallclock:** they also take `wallclock.py`'s session, with the native-suite truth.
- **Scoring:** gates and rules are unchanged. A pass-like verdict on a native-failing change is a
  false assurance (G1).

This amendment adds measurements and changes no threshold. It was written before any `verify` run
on hb-actions or wcd.
