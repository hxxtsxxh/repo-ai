## 2. Direct Answers to the 10 Audit Questions

1. **Does `repo-ai do --agent auto` actually select and invoke an installed external coding agent?**
   - **Disproved at `608170a`:** `runtime.plan()` (`src/repo_ai/mission/runtime.py:125-126`) hardcodes `decision = 'ASK_APPROVAL'` whenever `agent not in {'none', 'replay'}`, and `cmd_do` (`src/repo_ai/mission/cli.py:58-59`) raises `ValueError('live provider execution is planning-only; local execution requires --agent replay --replay FILE')`.
2. **Do the four provider adapters genuinely support the installed versions' CLI flags, output protocol, and usage/limit reporting?**
   - **Disproved in part at `608170a`:** Live testing against installed CLIs revealed:
     - `bob 2.0.6` (`bob run --help`) does **not** have `--sandbox workspace-write` (which was hardcoded in `adapters.py:92,162`), requires `--trust --disable-mcp --disable-subagents`, and outputs cost under `stats.session_costs` and tool count under `stats.tool_calls` (`{"type":"result","status":"success","stats":{"task_id":"...","session_costs":0.079234,"tool_calls":2},"last_message":"..."}`).
     - `claude 2.1.311` (`claude --help`) does **not** have `--max-turns` (which was hardcoded in `adapters.py:76,139`), requires `--verbose` when `--output-format stream-json` is used with `--print`, and requires `--` before the positional prompt when variadic `--tools` is passed.
     - `gemini 0.65.0` requires `--skip-trust` in disposable workspaces.
     - `codex 0.164.0` exits with code `0` even when emitting `{"type":"turn.failed","error":{"message":"You’ve hit your usage limit..."}}`.
     - `parse_event_stream` defaulted missing cost to `0.0` instead of `None` (`UNKNOWN`).
3. **Can a live provider's completed work flow through the same baseline/candidate verification, immutable acceptance tests, stale-evidence invalidation, and human-readable passport as the replay demo?**
   - **Confirmed once `adapters.py` and `runtime.py` wire live execution:** On this host, `bob 2.0.6` is live and authenticated (`claude` and `codex` are currently at their subscription usage limits and emit structured rate-limit events). Routing `bob 2.0.6` through `runtime.execute()` runs the exact same `observe(baseline)` -> `edit_candidate(run_provider + validate_workspace_edits)` -> `observe(candidate)` -> `regression()` pipeline and marks `provider.stage = "LIVE_VERIFIED"`.
4. **Can a second provider genuinely continue a first provider's partial/failed work via a redacted `HandoffCapsule`?**
   - **Disproved at `608170a`, being activated now:** `handoff` exported and verified capsules, but `do` / `mission resume` had no `--from-handoff <capsule.json>` consumer. Adding `--from-handoff` enables a live `claude`/`codex` rate-limit failure to hand off to live `bob` (or `replay`) while preserving contract constraints, verified facts, and remaining time budget.
5. **Does the conductor dispatch a multi-node plan and enforce a single integration owner?**
   - **Partially confirmed:** `scheduler.py` dispatches parallel read nodes (`impact`, `acceptance`) under `ThreadPoolExecutor` and enforces a single `write` node (`ExecutionDAG.validate()` at `contracts.py:127-128`), but `runtime.plan()` did not integrate `orchestrate.plan()` signals (`trivial`, `broad`, `risky`) or `security`/`skeptic` post-edit checks.
6. **Are tournament candidates truly isolated before comparison and integrated only after a fresh final verification run?**
   - **Confirmed (`tournament.py:46-99`, `runtime.py:328, 498-543`):** Each candidate executes in its own `materialize_commit` disposable workspace and runs full baseline + candidate + whole-change regression checks; no candidate is auto-applied to the working tree. Adding `repo-ai apply <id>` will verify freshness and run a post-apply verification check.
7. **Are changes to test helpers, runner selection, build toolchain, acceptance contracts, zone policy, provider binary, runtime reporter, and dependencies sufficient to stale affected evidence?**
   - **Mostly confirmed, with one gap found by audit:** `kernel_identity()` hashes `mission/`, `verify/`, and `providers/`; `status()` checks `source.fingerprint`, `kernel_identity()`, `check_privacy()`, and `evidence.environment_check()`. However, `status()` did **not** re-check `provider.identity_sha256` against the on-disk provider binary or verify that `baseline.pin.test_inputs` still match current disk bytes if untracked test helpers changed. We are closing both gaps in Phase II.
8. **Does the claimed `mission-eval` win reflect a fair independent baseline or only a deliberately naive fixture?**
   - **Deliberately naive & self-graded at `608170a`:** `eval_protocol.py:124-135` hardcoded `naive_false_pass = True` without running a test process, and `reality_engine_verified` graded itself using the same in-repo tests that `compare_candidates` used. We are replacing this with empirical smoke-test execution, held-out `independent_grader_tests` unseen by the tournament, a negative-control abstention task, and a preregistered multi-arm study protocol with `comparative_lift_verdict: "NOT_YET_DEMONSTRATED"`.
9. **Does the installed wheel behave identically to editable source?**
   - **Confirmed for `5f7e6df`/`608170a`:** Direct wheel and sdist-rebuilt wheel had identical SHA-256 (`891093ee7026f8227deae308b58bebb8d50d00528f859c52a48d701d2e4486c0`). Will be re-verified after Phase II code changes.
10. **What single missing workflow most prevents a skeptical developer from using `repo-ai` as their daily engineering tool today?**
    - **Closed-loop execution and working-tree application:** Running `repo-ai do "<task>" --run` with a real provider (or `--agent auto`), continuing across provider rate limits via `--from-handoff`, and applying the verified patch to the working tree via `repo-ai apply <mission-id>`.
